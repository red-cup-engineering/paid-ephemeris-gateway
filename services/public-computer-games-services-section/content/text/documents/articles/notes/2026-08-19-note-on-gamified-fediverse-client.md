**Status.** The server is real, deployed, and federating. `@red-cup-engineering/activitypub-services-section`
— a standards-conformant Fedify-based ActivityPub server (actor dispatch, inbox/outbox, WebFinger,
NodeInfo, signed delivery) — runs in production at `https://ap.561.group` (GCE
`bare-cedar-fog-cloud-mirror`, Caddy/Let's Encrypt, systemd user units, SQLite state on real disk),
with three live actors (`instance`, `crucible`, `ruinfold`) and daily posting timers. Signed
delivery round-trips against an independent public instance (`mastodon.social`); follower broadcast
and per-object dereference — the two gaps this program's own 2026-08-19 feasibility pass named —
are fixed and proven live as of the 2026-08-20 redeploy (temp-follower Follow→Accept→signed-`Create`
round trip, `DataIntegrityProof` intact). Full operational detail:
`activitypub-services-section/content/text/documents/notes/2026-08-19-note-on-ap-561-group-live-deploy-runbook.md`
and its `logs/2026-08-19-ap-561-group-deploy-log.md`. **What does not exist is the game layer**: no
rendering, world-model, or game-loop code anywhere in the "Semioverse"-named sections, and no
federation-delivery latency is being logged yet — the metric this program's own causal-set geometry
mechanic depends on has not started accumulating.

## What Moose is

This carrier founded as a stub for "the gamified Fediverse client" — an ActivityPub *client* that
would turn the public Fediverse into an MMORPG from one instance's point of view
(`2026-08-19-note-on-gaming-enterprises-vision.md`, "The gamified Fediverse client"). That framing
undersold what the house actually built. The house does not merely watch the Fediverse from a
client; it operates a real ActivityPub *server*, on owner metal, with its own actors already
federating. **Moose (owner-named 2026-09-02) is the server product**: the house's own instance,
its own actors, and — once the game layer lands — a world whose regional geography is measured from
that server's real relationships with every other reachable instance, not authored by a designer and
not merely rendered by a client watching someone else's server. The client-side idea is not
abandoned; it is now one face of a server-first product, the same relationship the Palaverse section
of the vision note already states for federation generally: "a follower's own client timeline is
meant to become the Today page" — but the world Moose computes is generated by Moose's own server,
federating outward, not assembled by a client parsing whatever it happens to receive.

## MMORPG design commitments

- **The world's geography is measured, not authored.** Wilder Conceptions item 6
  (`science-services-section/.../gaming-services-section/content/text/documents/articles/notes/2026/08/19/2026-08-19-note-on-wilder-conceptions-01.md`
  §6, "The federation is the map: don't design the world's geometry, measure it"): real signed
  round-trip delivery latency between `ap.561.group` and every other reachable federated instance
  becomes the literal spacelike/timelike separation of Commons regions, populating the causal-set
  event structure `shrimp-ecology-brief-v2.md` §1 already specifies (a Poisson-sprinkled causal set
  with apex/void cones). This is the same destination as the SHRIMP undersea MUD and the Commons,
  "approached from three sides: humans-as-actors, agents-as-actors, and the shared world they act
  in" (`2026-08-19-note-on-gaming-enterprises-vision.md`, "The gamified Fediverse client").
- **Each game/actor is a first-class Fediverse identity.** Per the Palaverse section of the vision
  note: "each game is an ActivityPub actor (crucible@…, durante@…) posting its daily seed, results,
  and replay links; a follower's own client timeline is meant to become the Today page" — proven
  live 2026-08-20 for `crucible@ap.561.group`.
- **An intent log is an Activity.** The vision note states this identification directly, meaning the
  Cartridge contract every house game already implements is not a separate format Moose must
  translate — it composes with ActivityPub natively.
- **Federated, not centralized.** Unlike every incumbent persistent-world game (see meet-then-beat
  below), Moose's own instance is one federated peer among independently-operated others — the
  causal-set input exists because of that structural fact, not despite it.

## Meet-then-beat

**Arena and receiver.** A player (human or agent) who entrusts a persistent multiplayer world with
their time, deciding where to spend it based on what that world's space and their place in it
actually mean. The bounded comparison: products that give a receiver a persistent shared world to
inhabit and move through, evaluated on world-space, presence, and economy — not on generic
Fediverse social software, which is a complement (an ordinary Mastodon client is how a Palaverse
follower already receives the Today page; it is not competing to be the world).

**Incumbent portfolio, classified.**

| Product | Role | Basis |
|---|---|---|
| EVE Online, Albion Online | Same-job incumbent (persistent shared world) | Already the house's own comparison class for the wider Commons vision (`2026-08-19-note-on-gaming-enterprises-vision.md`, "Closest reference points: Albion Online's player-driven world meets EVE's daily regeneration") |
| Mastodon, GoToSocial, Misskey/Akkoma | Upstream provider / reference implementation | Other ActivityPub server software Moose's own Fedify-based server must interoperate with, not compete against, for the game-world job |
| Ordinary Fediverse clients (any Mastodon app) | Complement | Receives the Today page a Moose actor posts; not a rival for world-inhabitance |
| A shipped ActivityPub-native persistent game world | Same-job incumbent, sought and not found | A 2026-09-02 search (web + corpus) found no shipped product combining ActivityPub federation with a persistent multiplayer world; the closest hit is a thought-piece proposal ("Can we Game in the Fediverse?", kevinhoffman.blog) naming the idea as unrealized, not a built incumbent to measure against |
| "Matisse: Visualizing Measured Internet Latencies as Manifolds" (arXiv:2509.08097) | Reference implementation for the mechanic, not a competitor | External, independent research validating that deforming a space by measured internet latency is a real, working technique — corroboration that the causal-set mechanic's underlying method is not house-invented from nothing |

**BEAT hypothesis, falsification-checked.** *Because Moose's own instance federates with
independently-operated peers it does not control, real signed-delivery round-trip latency between
those peers is a structural fact no centralized world operator possesses (EVE and Albion run on
infrastructure they fully own, so they have no independent peers to measure); Moose can therefore
derive a world geometry from genuine external network reality under the assay "logged round-trip
latency between `ap.561.group` and N independent public instances correlates with the map's own
derived region distances," while no named incumbent can produce the same result without first
acquiring federated peers they do not control — which would contradict their own centralized
architecture.* Checked against every named incumbent's measured surface (none offer federated
peers) and actively searched for a counterexample (none found shipped, per the web search above).
**Falsification already run in-house, not deferred**: Wilder Conceptions item 6's own "Honest reason
this might be wrong" flags that real latency is noisy, adversarial (a remote admin could throttle a
peer to grief the game's geography), and non-stationary in a way a research causal-set sprinkling
is not — literal latency-as-geometry risks a map that reshapes for reasons unrelated to play. The
item's own outcome already narrows the claim: "geometry deferred... measured latency as an *input*
to an authored map may be the survivable version." Moose inherits that narrowed claim rather than
the stronger, already-rejected one.

## Uncertainties honestly held

- Whether measured latency should ever be *literal* world geometry, or only an input damped by an
  authored map, is an open design question the house's own prior pass could not resolve — see the
  falsification note above.
- x402 payment execution is conceptually scaffolded inside the ActivityPub layer (a pass-through
  payload type that can ride inside a federated A2A message) but not executed anywhere examined: no
  challenge/response, no payment verification, no settlement witness. Whether Moose needs it before
  a game layer exists is unresolved.
- `SemioticExchange.sol`, the settlement chain occasionally named alongside this program, is real and
  mostly passes its own tests but has never been compiled or deployed to any chain — it is not a
  dependency of anything above and should not be assumed load-bearing for Moose without a separate
  decision.
- Whether "the gamified Fediverse client," "the Palaverse," and Moose are one program or three
  overlapping ones is a naming question the vision note itself has not fully settled; this carrier
  takes the position that Moose is the server-product frame the other two compose under, per the
  owner's 2026-09-02 naming, but that composition has not been separately ruled on.

## Current program edge

The smallest first step this program ever named — deploy the existing ActivityPub server to a
reachable public endpoint (`2026-08-19-note-on-semioverse-architecture.md`'s own "smallest honest
first step") — is done: `ap.561.group` is live, federating, and verified against an independent
instance. **The next roadmap item is the one this program named as following it and has not yet
taken**: log real federation-delivery latency as a first-class metric on every outbound delivery
attempt, extending `provider.mjs`'s existing `publish()`/`sendActivityToFollowers` path to record
round-trip time per delivery target. It requires no game code
(`2026-08-19-note-on-wilder-conceptions-01.md` §6: "log delivery latency as a first-class metric
from day one... so the causal-set data is being collected the moment federation starts working").
**Acceptance assay**: a dated record under `activitypub-services-section/data/records/` holding
logged round-trip latency for real signed deliveries to at least one external public instance
(`mastodon.social`, the same instance the live round-trip was already verified against) across a
stated number of delivery attempts — the first real data this program's causal-set geometry
mechanic could be built against.
